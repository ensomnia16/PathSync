# 双副本同步模型

本工具定时比较两份目录。设计依据是 Unison 的双副本文件同步规范，而不是用两次单向复制模拟双向同步。Unison 将每个路径的状态定义为文件、目录、符号链接或“不存在”，并保存上次成功同步的共同状态（archive）。

资料：

- Pierce 与 Vouillon，[A Formal Specification and Reference Implementation of a File Synchronizer](https://www.cis.upenn.edu/~bcpierce/papers/unisonspec.pdf)，第 4–5、8、10 节。
- [Unison 官方手册：What is an Update? / Reconciliation](https://github.com/bcpierce00/unison/blob/master/doc/unison-manual.tex)。
- [Syncthing Block Exchange Protocol](https://docs.syncthing.net/specs/bep-v1.html)：删除标记、不可用标记与版本向量的区别。
- Saito 与 Shapiro，[Optimistic Replication](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-2003-60.pdf)，第 6.5 节：固定期限清除删除标记并不严格安全。
- [Microsoft OneDrive Files On-Demand for Mac](https://support.microsoft.com/en-us/onedrive/save-disk-space-with-onedrive-files-on-demand-for-mac)：Finder 中可见的在线文件可能尚无本地内容。

## 状态与判定

对路径 `p`，`A` 是上次成功一致的共同状态，`L` 和 `C` 是本轮读到的本地与 OneDrive 文件夹状态。文件状态以内容哈希表示；`∅` 表示确认不存在。读取失败、扫描失败、在线占位符内容不可用属于 `?`，不能当作 `∅`。

实现用大小、修改时间和文件状态变更时间做快速筛查；这些值变化时再读内容计算 SHA-256。它们只是减少读取量的缓存依据，不能把文件时间戳当作因果时钟。若其他程序刻意保留全部这些元数据却替换内容，当前快速筛查仍可能漏检；严格内容判定需要每轮读取并哈希所有文件。

| 条件 | 结果 |
| --- | --- |
| `L = C` | 接受共同状态；若存在未完成的保留冲突，先完成恢复检查 |
| `L = A, C ≠ A` | 云端变化按同步方向传播到本地 |
| `C = A, L ≠ A` | 本地变化按同步方向传播到云端 |
| `L ≠ A, C ≠ A, L ≠ C` | 冲突；不从内容或修改时间推断因果先后 |
| 任一侧为 `?` | 停止该路径的写入，不推进共同状态 |

删除是 `∅`，遵循同一判定。单侧删除若符合选定方向，会在确认目标未变并备份后传播；方向相反则跳过，不会把删除误当作新增。修改时间只供用户选择“保留较新”时裁决冲突，不参与变化或并发判定。

## 执行顺序与持久状态

1. 扫描两侧并读取所需内容；目录扫描失败时不得推断文件缺失。
2. 比较共同状态，产生传播、冲突或跳过的决定。
3. 任何覆盖和本工具执行的删除，先保存并校验目标备份。复制先写临时文件，复查两侧内容，再替换目标。
4. 仅在操作完成后推进该路径的共同状态。已确认双方都不存在的路径保留 `∅` 状态，不使用 15 天备份期限清理它。
5. “保留两个”先持久记录操作意图，再创建并核验冲突副本。中断后重新检查主文件和副本，才能转为待人工审核。

目录级冲突在逐文件处理前判定。如果一侧删除了曾同步的目录，而另一侧的子树相对 anchor 增删或修改了文件，或增加了空子目录，整个子树会暂停自动处理并持续显示一条目录冲突。用户手动让两侧子树一致，或将保留侧改回 anchor 后，下一次同步才移除这道屏障。这样不会在报告一个子文件冲突的同时继续删除其未修改的兄弟文件。

对已经“保留两个”的冲突，手动选择“采用当前较新版本”时比较当前主文件与保留副本的修改日期。保留副本必须在两侧一致。主文件两侧若不同，只有一侧相对 anchor 更新时，才能在这次操作中先备份并传播该版本；若两侧都更新，仍须人工处理。日期相同时不自动裁决。这个操作使用点击时的当前版本，因此主文件在保留后继续编辑，也可以被明确选中；冲突副本仍会保留。

外部应用已经完成的删除发生在本工具运行之前，本工具无法为被删内容补做备份。需要恢复这类删除时，必须依赖先前备份或其他版本历史。

## 尚未解决的边界

- 目录级冲突目前由用户在文件管理器中整体处理，界面不提供“一键采用整棵目录树”。普通文件同步不复制空目录，也不自动删除已经空了的目录节点；目录元数据和符号链接仍不参与同步。
- OneDrive 文件夹是 macOS File Provider 展示的本地视图，不是 OneDrive 服务器的一致快照。离线、占位符读取失败以及云端尚未同步到这台 Mac 的修改，无法仅凭本地扫描可靠判定。运行前须确认 OneDrive 已同步并且目录内容可读；工具不会把已报告的扫描或读取错误当作删除。
- 文件系统替换和 JSON 状态文件写入不是跨两份目录的原子事务。测试覆盖中断后的“保留两个”恢复，但尚未证明所有崩溃点都能自动修复。实际部署前还需完整的故障注入测试。
- 仅凭两份目录快照，无法区分“另一个离线设备迟到的旧文件”和“删除后重新创建的新文件”。Syncthing 的版本向量依赖所有参与设备共同维护版本历史；本工具不能从 OneDrive 文件夹路径凭空获得这段因果历史。
